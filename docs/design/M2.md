# M2 design — catalogue, drivers, buses, uploads

Status: approved for implementation · Milestone M2 · Inputs: `docs/PARITY_MATRIX.md` (rows
marked M2), ADRs 0001–0013.

M2 delivers the static side of the product: the transport network (stops, lines, ordered line
stops, line geometry, timetables, disruptions, journey planning), the driver programme (driver
applications with identity documents and an explicit state machine), the fleet (buses, their
approval and their line assignments) and private object storage for photos and documents.
Real-time tracking is M3; notifications to passengers are M5.

This document is the contract for every work package (WP). Where it is silent, follow the
existing M1 code and the ADRs. Where the code and this document disagree, this document wins
and the code is fixed.

---

## 1. Cross-cutting rules

### 1.1 Layering (unchanged from M1)

* `crates/domain` — value objects, entities, state machines, pure algorithms. No I/O, no async,
  no `sqlx`/`axum` types. Unit-tested (proptest where invariants exist).
* `crates/app` — one module per bounded context (`storage.rs`/`uploads.rs`, `network/`,
  `drivers/`, `fleet/`, `disruptions.rs`, `journeys.rs`); ports (traits) in `ports.rs` or in a
  `ports` submodule of the context; services take `Arc<dyn Port>`; every use case starts with
  `Policy::authorize(actor, &Action::…)`; unit tests with fakes (fakes may live next to the
  tests of the context, e.g. `drivers/tests.rs`, or in `testing.rs`).
* `crates/infra` — `pg/<context>.rs` implements the repository ports for `PgStore` with
  `sqlx::query!`/`query_as!` (compile-time checked, parameterized); storage adapter in
  `storage.rs`.
* `crates/api` — `routes/<context>.rs`, request/response DTOs (in `dto.rs` or a `dto/`
  module), `utoipa::path` on every handler, registration in `routes/mod.rs`, tag in
  `openapi.rs`.
* Composition: new services are added to `dz_infra::wiring::Services`, `AppServices`
  (`crates/api/src/state.rs`), `bin/dz-api/src/main.rs` and `crates/testkit/src/app.rs`.

### 1.2 Authorization

* Coarse: `RequirePermission<perm::X>` in the handler signature (anonymous callers hold
  `catalog:read`, `bus:read`, `tracking:read`, so public reads use those markers).
* Fine: extend `dz_domain::authz::Action` with resource actions and implement them in
  `Policy::authorize` — e.g. `ReadDriver { owner: UserId }`, `ManageOwnBus { owner: UserId }`.
  Deny by default; add the rows to the policy unit tests.
* Ownership is always taken from the authenticated actor, never from the request body
  (legacy L-02, L-05). Another user's private resource is a `404`, not a `403`, when its
  existence would otherwise leak (driver profiles, non-public buses).
* Visibility: catalogue reads are public and show active rows only; callers holding the
  corresponding write permission (`stop:write`, `line:write`, `schedule:write`,
  `disruption:write`, `bus:manage`) also see inactive rows and may filter on activity.

### 1.3 Writes, audit and side effects (transactional outbox)

* Every administrative mutation (anything an admin or API key does that is not
  self-service) writes an `audit_log` entry **in the same transaction** as the change.
  Actions are named `<resource>.<verb>` (`stop.create`, `line.update`, `line.stops.replace`,
  `schedule.delete`, `driver.approve`, `bus.reject`, `bus.line.assign`, `disruption.create`…).
* Side effects that must happen after the change (e-mails, deleting replaced objects) are jobs
  inserted into `jobs` **in the same transaction** (transactional outbox, legacy L-08). WP1
  introduces the shared mechanism:

  ```rust
  // crates/app/src/ports.rs
  pub struct OutboxJob { pub job: Job, pub options: JobOptions }
  /// What a repository write must persist atomically with the change itself.
  #[derive(Default)]
  pub struct WriteEffects { pub audit: Vec<NewAuditEntry>, pub jobs: Vec<OutboxJob> }
  ```

  and `dz_infra::pg::effects::persist(tx, &WriteEffects)` (inserts audit rows + jobs in the
  caller's transaction; job insertion shares its SQL with `PgJobQueue::enqueue`, including the
  `dedup_key` rule). Repository write methods take `effects: WriteEffects` as last argument.
  The private `audit_entry` helper of `admin.rs` moves to `crates/app/src/audit.rs` (`pub(crate)
  fn entry(actor, meta, at, action, resource_type, resource_id, details)`), used by all
  contexts.
* New `Job` variants are added to `dz_app::jobs::Job` with their runner in `JobRunner`, tests,
  and (for periodic ones) a `CRON_SCHEDULE` entry.

### 1.4 HTTP contract

* Paths and verbs exactly as in §3–§7. Kebab-case path segments, no trailing slash, ids are
  UUIDs (`PathId` extractor: malformed → 404).
* Request DTOs: `#[serde(deny_unknown_fields)]`, `validator` attributes for shape (lengths,
  ranges), domain parsing for semantics; field errors use existing `Violation` codes
  (`required`, `too_long`, `out_of_range`, `invalid_choice`, `invalid_format`, …). Add a
  `Violation` only when no existing one fits, with i18n texts.
* PATCH = partial update with `Option<T>` (and `double_option` for nullable fields); it returns
  the **full** resource. Unknown fields → 422 `unknown_field`. Read-only/immutable fields are
  simply absent from PATCH DTOs (→ `unknown_field`), e.g. `lines.code`.
* Creation: `201 Created` + `Location` header + full resource. `Idempotency-Key` works through
  the existing middleware (responses carrying presigned upload URLs are `no-store`).
* Lists: cursor pagination (`?cursor=&limit=`, default 20, max 100, ordered by
  `(created_at DESC, id DESC)` with the existing `Cursor`/`PageRequest`/`Page` types) and an
  explicit allow-list of filters (typed query DTO with `deny_unknown_fields`). Exceptions are
  stated per endpoint (bounded, naturally ordered lists such as a line's stops).
* Errors: RFC 9457 problem documents. Every new `code` gets fr/ar/en texts in
  `crates/api/src/i18n.rs` and is added to the translation-completeness test. New conflict
  kinds are new `ConflictKind` variants (domain) mapped to `409`.
* Coordinates: JSON `{"lat": 36.7538, "lng": 3.0588}` (WGS 84, degrees; lat ∈ [-90, 90],
  lng ∈ [-180, 180], finite). Geometries: GeoJSON (`{"type":"LineString","coordinates":[[lng,
  lat], …]}` — GeoJSON order is lng, lat). Distances in metres (`*_m`), durations in seconds
  (`*_s`), times of day `"HH:MM"` (24 h), weekdays ISO 8601 (1 = Monday … 7 = Sunday).
* Public responses never contain PII of drivers (names beyond first name, phone, document
  numbers, document photos) or of other users.

### 1.5 Database

* One migration file per WP, named `2026100800000N_<topic>.sql` (N = 5 for WP1 … 9 for WP5),
  forward-only, with comments explaining each constraint and index. Indexes must serve a
  query in the code; justify non-obvious ones with the `EXPLAIN` shape in a comment.
* Invariants in the schema (checks, FKs, exclusion constraints) and mapped to typed errors via
  constraint names (`violated_constraint`).
* Timestamps `timestamptz` set from the injected `Clock` (not `now()`), so fakes and SQL agree.
* Spatial: `geography` columns, `ST_DWithin`/`<->`/`ST_Distance` in SQL; never compute
  distances for many rows in Rust.

### 1.6 Definition of done (every WP)

1. `cargo clippy --workspace --all-targets -- -D warnings` is clean (do **not** run
   `cargo fmt`; keep rustfmt style by hand: max width 100, `use_small_heuristics = "Max"`).
2. `cargo test --workspace` passes: unit tests for domain/app logic, and API tests in
   `crates/testkit/tests/<context>.rs` for **every** endpoint covering success, validation
   (422), unauthenticated (401), forbidden (403), not found (404), conflicts (409) and the
   visibility rules; plus repository-level tests for constraints/races where relevant.
3. Migrations applied to the dev database; `cargo sqlx prepare --workspace -- --all-targets`
   regenerated (`.sqlx/`), `cargo sqlx prepare --workspace --check -- --all-targets` passes.
4. `docs/openapi.json` regenerated (`cargo run -q -p dz-api -- openapi > docs/openapi.json`).
5. No `todo!`, `unimplemented!`, `TODO`, placeholder handlers or ignored tests.
6. `docs/PARITY_MATRIX.md` rows updated if the delivered contract differs from the row.

## 2. WP1 — object storage, uploads, avatars, outbox

### 2.1 Storage adapter

* Crates: `rusty-s3` (presigning, pure) + `reqwest` (async, rustls, already in the lock
  file) for server-side `HEAD`/`DELETE` signed with the same credentials.
* Config `DZ_STORAGE__*` (`crates/config`): `endpoint` (URL the API uses), `public_endpoint`
  (optional URL embedded in presigned URLs for clients; default = endpoint), `region`
  (default `us-east-1`), `bucket`, `access_key_id`, `secret_access_key` (secret, redacted),
  `path_style` (default `true`), `upload_ttl_secs` (default 900, 60–3600),
  `download_ttl_secs` (default 3600, 300–43200), `request_timeout_ms` (default 5000).
  Storage is optional: when `endpoint` is unset, upload/attach endpoints answer
  `503 storage_unavailable` and `*_url` fields are `null`. Production requires it and an
  `https` public endpoint.
* Port `ObjectStorage` (`crates/app`):
  * `presign_put(key, content_type, size_bytes, expires_in) -> PresignedUpload { url, method:
    "PUT", headers: [("content-type", …), ("content-length", …)], expires_at }` — content type
    and length are **signed**, so the client cannot upload something else or something bigger.
  * `presign_get(key) -> Url` — the signing time is truncated to the start of the current
    hour and the validity is `download_ttl_secs` + 1 h, so the URL is stable within an hour
    (ETags of resources embedding it stay valid).
  * `head(key) -> Option<ObjectInfo { size_bytes, content_type }>`; `delete(key)` (idempotent).
  * Errors map to `AppError::Unavailable("storage")`.
  * A fake (`FakeObjectStorage`, in-memory) for unit tests.
* Object keys are generated by the server only: `<purpose>/<upload_id>` (no account id: public photo URLs must not reveal the uploader) — never
  from client file names.

### 2.2 Uploads

Migration `…05_uploads.sql`: table `uploads (id uuid PK, owner_id → users ON DELETE CASCADE,
purpose text CHECK IN ('avatar','driver_id_card','driver_license','bus_photo','stop_photo'),
object_key text UNIQUE, content_type text, size_bytes integer > 0, status text CHECK IN
('pending','attached'), created_at, expires_at, attached_at, CHECK ((status = 'attached') =
(attached_at IS NOT NULL)))` with a partial index on `expires_at WHERE status = 'pending'`.

| Purpose | Allowed types | Max size | Permission to request |
|---|---|---|---|
| `avatar` | image/jpeg, image/png, image/webp | 2 MiB | `account:self` |
| `driver_id_card`, `driver_license` | image/jpeg, image/png, image/webp, application/pdf | 10 MiB | `driver:apply` |
| `bus_photo` | image/jpeg, image/png, image/webp | 5 MiB | `bus:register` or `bus:manage` |
| `stop_photo` | image/jpeg, image/png, image/webp | 5 MiB | `stop:write` |

* `POST /api/v1/uploads` — body `{purpose, content_type, size_bytes}` → `201` `{id, purpose,
  content_type, size_bytes, upload: {method, url, headers{}}, expires_at}`,
  `Cache-Control: no-store`. Uploads are owned by a human account: API keys get `403`
  (they can still manage stops, but not attach photos).
* `GET /api/v1/uploads/{id}` — the caller's upload (status `pending`/`attached`, timestamps,
  never the presigned request again); others' uploads are `404`. This is the `Location` of
  the `201`.
* **Claiming** (used by every "attach" endpoint): `app::uploads::claim(owner, upload_id,
  purpose)` checks the row (exists, owned by the caller, same purpose, `pending`, not
  expired — otherwise `422` on the `upload_id` field with code `invalid_upload`), then `HEAD`s
  the object (missing → `422 invalid_upload`; size or content type different from the
  declaration → `422 invalid_upload` and the object is deleted). The resource repository marks
  the upload `attached` **in the same transaction** that stores the key, with
  `UPDATE uploads SET status = 'attached' … WHERE id = $1 AND status = 'pending'` — zero rows →
  `409 upload_already_used` (race).
* Replaced or removed objects are deleted by a `StorageDeleteObject { key }` job enqueued in
  the same transaction (outbox).
* Cron `purge_expired_uploads` (hourly): deletes pending uploads older than `expires_at` + 1 h
  and their objects (batch of 500 per run, `StorageDeleteObject` per object or direct delete).

### 2.3 Avatars

* `PUT /api/v1/me/avatar` `{upload_id}` → `200` `ProfileDto` (with `avatar_url`).
* `DELETE /api/v1/me/avatar` → `204` (object deleted by job).
* `ProfileDto` gains `avatar_url: string|null` (presigned GET).

### 2.4 Test infrastructure

* `dz-testkit` starts `rustfs/rustfs:1.0.1` (S3-compatible; MinIO images are no longer
  published) unless `DZ_TEST_S3_URL` is set, creates one bucket per test (`dz-t-<uuid>`) and
  configures `DZ_STORAGE__*`. Helper `TestApp::upload(account, purpose, content_type, bytes)`
  performs the full presign → PUT → returns `upload_id`.
* CI: add a RustFS service container and `DZ_TEST_S3_URL`.
* `compose.yaml`: optional `storage` profile with RustFS (internal network) and a one-shot
  bucket creation; production may point `DZ_STORAGE__*` to any S3 provider instead.

## 3. WP2 — network catalogue

Migration `…06_network.sql`: `CREATE EXTENSION pg_trgm`; trigram GIN indexes for search
(`stops (name)`, `lines ((code || ' ' || name))`); any column additions needed below.

Domain (`crates/domain/src/geo.rs`, `network.rs`): `GeoPoint` (validated lat/lng, haversine
distance for tests and the planner), `LineGeometry` (2–10 000 points, no consecutive
duplicates), `LineCode` (1–20 chars `[A-Za-z0-9-]`, stored upper-case, immutable), `HexColor`
(`#RRGGBB`, stored upper-case), `StopName`, `TimeOfDay` window (`start < end`), `Weekday`
(1–7), frequency 1–1440 min, fare ≥ 0 DZD.

## 4. WP3 — drivers

Migration `…07_drivers.sql`: `driver_status_log (id, driver_id → drivers, from_status NULL,
to_status, reason, changed_by → users ON DELETE SET NULL (NULL = system), created_at)` with an
index `(driver_id, created_at DESC, id DESC)`; append-only (UPDATE/DELETE rejected by trigger,
like `audit_log`).

Domain (`crates/domain/src/driver.rs`): `DriverStatus` and the **transition table**

| From \ action | apply | approve | reject | suspend | reinstate | reapply | documents changed |
|---|---|---|---|---|---|---|---|
| (none) | pending | | | | | | |
| pending | | approved | rejected | | | | pending |
| approved | | | | suspended | | | pending |
| rejected | | | | | | pending | rejected |
| suspended | | | | | approved | | suspended |

Anything else is `409 invalid_transition`. Reject and suspend require a `reason` (1–1000
chars). Value objects: national ID number (18 digits), licence number (1–20 `[A-Za-z0-9-]`),
phone (existing `PhoneNumber`), years of experience 0–60.

| Method & path | Permission | Notes |
|---|---|---|
| `POST /api/v1/drivers/applications` | `driver:apply` | `{phone_number, id_card_number, id_card_photo_upload_id, driver_license_number, driver_license_photo_upload_id, years_of_experience}` — profile bound to the caller (L-02), one transaction (L-31): driver row + status log + both uploads claimed + outbox job notifying admins. `409 driver_profile_exists`, `409 id_card_taken`, `409 license_taken`. → `201` own `DriverDto`. |
| `GET /api/v1/drivers/me` | `account:self` | 404 if the caller has no driver profile. |
| `PATCH /api/v1/drivers/me` | `account:self` | `{phone_number?, years_of_experience?, id_card_number?, id_card_photo_upload_id?, driver_license_number?, driver_license_photo_upload_id?}` — any document field change on an `approved` profile sends it back to `pending` (logged, admins notified, old objects deleted by job). |
| `PUT /api/v1/drivers/me/availability` | `account:self` | `{is_available}`; approved drivers only (`409 invalid_state` otherwise). |
| `POST /api/v1/drivers/me/reapply` | `driver:apply` | `rejected → pending`; logged; admins notified (L-24). |
| `GET /api/v1/drivers` | `driver:read` | Admin list; filters `status`, `is_available`; cursor pagination. |
| `GET /api/v1/drivers/{id}` | `driver:read` or own profile | Others' profiles → 404. |
| `GET /api/v1/drivers/{id}/status-history` | `driver:read` or own profile | Newest first, cursor pagination, includes `changed_by` (user id) and reason. |
| `POST /api/v1/drivers/{id}/approve` | `driver:review` | `pending → approved`; the user's role becomes `driver` in the same transaction (no session revocation needed: a privilege gain takes effect at the next refresh). |
| `POST /api/v1/drivers/{id}/reject` | `driver:review` | `{reason}`; `pending → rejected`. |
| `POST /api/v1/drivers/{id}/suspend` | `driver:review` | `{reason}`; `approved → suspended`; same transaction: `is_available = false`, all the driver's buses `status = 'inactive'` (L-25). |
| `POST /api/v1/drivers/{id}/reinstate` | `driver:review` | `suspended → approved`. |

* `DriverDto` (owner/admin): id, user `{id, email, first_name, last_name}`, phone,
  id_card_number, driver_license_number, `id_card_photo_url`, `driver_license_photo_url`
  (presigned GET; owner and `driver:read` only), years_of_experience, status, status_reason,
  status_changed_at, is_available, rating (`rating_sum / rating_count` rounded to 2 decimals or
  null) and rating_count, created_at, updated_at. There is no public driver endpoint in M2.
* Every transition: status log row (with actor), audit entry for admin actions, outbox job
  `DriverStatusChanged { driver_id, status }` → localized e-mail to the driver (fr/ar/en
  templates in `mail.rs`), and for apply/reapply/documents-changed `DriverReviewRequested
  { driver_id }` → e-mail to every active admin.
* Approved drivers keep role `driver` when suspended (they must still be able to see their
  status); driving capabilities check `status = approved` (buses in WP4, trips in M3).

## 5. WP4 — buses and line assignments

Migration `…08_fleet.sql`: `bus_line_assignments (bus_id → buses ON DELETE CASCADE, line_id →
lines ON DELETE RESTRICT, assigned_at, assigned_by → users ON DELETE SET NULL, PRIMARY KEY
(bus_id, line_id))` + index `(line_id)`; any `buses` additions needed.

Domain (`crates/domain/src/bus.rs`): licence plate (Algerian format `NNNNN-NNN-NN`, 1–5
digits, 3 digits, 2-digit wilaya code 01–58), year 1950..=current+1, capacity 1–300, average
speed 5–120 km/h, `BusType`, `BusStatus` (`active`/`inactive`/`maintenance`),
`ApprovalStatus` (`pending`/`approved`/`rejected`), features (≤ 20 tags, each 1–40 chars
`[a-z0-9_]`). A bus is **operational** when approved, active and its driver is approved.

| Method & path | Permission | Notes |
|---|---|---|
| `POST /api/v1/buses` | `bus:register` | The caller's driver profile must be approved (`409 driver_not_approved`). Owner = caller's driver profile (L-05). Starts `pending`. `409 license_plate_taken`. |
| `GET /api/v1/buses` | `bus:read` | `?owner=me` → the caller's buses (any state; requires a driver profile). Admins (`bus:manage`): all, filters `approval_status`, `status`, `driver_id`, `line_id`. Everyone else: operational buses only, filter `line_id`. Cursor pagination. |
| `GET /api/v1/buses/{id}` | `bus:read` | Owner/admin: `BusDto`; others: `PublicBusDto` if operational, otherwise 404. |
| `PATCH /api/v1/buses/{id}` | owner (`bus:register`) or `bus:manage` | Owner: descriptive fields only (model, manufacturer, year, capacity, bus_type, is_air_conditioned, features, description, average_speed_kmh). Admin: also `license_plate` and `status`. Others → 404/403 per §1.2. |
| `DELETE /api/v1/buses/{id}` | owner while not approved, or `bus:manage` | Cascades assignments. Audited for admins. (M3: refused once trips exist.) |
| `POST /api/v1/buses/{id}/approve` | `bus:manage` | `pending|rejected → approved`. Outbox e-mail to the owner. |
| `POST /api/v1/buses/{id}/reject` | `bus:manage` | `{reason}` (stored, L-45); `pending|approved → rejected`. Unassigns nothing (assignments stay but the bus is not operational). |
| `POST /api/v1/buses/{id}/activate`, `/deactivate` | `bus:manage` | `status` active/inactive (M3: deactivation ends an active trip). |
| `PUT /api/v1/buses/{id}/photo` / `DELETE` | owner or `bus:manage` | `{upload_id}` purpose `bus_photo`. |
| `GET /api/v1/buses/{id}/lines` | `bus:read` | Same visibility as the bus. |
| `PUT /api/v1/buses/{id}/lines/{line_id}` | `bus:manage` | Upsert assignment (L-50): `201` when created, `200` when it already existed. Audited. |

### 6.1 Disruptions

### 6.2 Journey planner

`GET /api/v1/journeys?from_stop_id=&to_stop_id=&max_transfers=(0–2, default 1)&limit=(1–5,
default 3)` [`catalog:read`].

* Pure algorithm in `crates/domain/src/journey.rs` over a `Network` snapshot (active lines
  with their ordered stops, per-segment time, line headway). Lines are ridden in both
  directions. Inactive stops cannot be boarded or alighted at but their segments count.
* Segment time = `time_from_previous_s`, else `distance_from_previous_m` at the line's
  reference speed (20 km/h), else straight-line distance (haversine) × 1.3 at 20 km/h.
* Waiting time per boarding = half the headway (`frequency_minutes` of the line, else the
  shortest active schedule frequency of the line, else 15 min). Transfer penalty 180 s.
* Search: round-based (RAPTOR-style) or label-setting over (stop, transfers) states; returns up
  to `limit` Pareto-optimal options by (transfers, total time), each with legs `{line {id,
  code, name, color}, board_stop, alight_stop, direction (+1/-1), stops_count, ride_time_s,
  distance_m, wait_time_s}` and totals. Same from/to → 422. No path → `200` with `[]`.
* The snapshot is loaded with one query and cached in-process for 30 s (invalidated on
  catalogue writes in the same process; other replicas converge within the TTL).
* Property tests: options are sorted, legs connect, never board at inactive stops, total time
  equals the sum of parts, transfers ≤ max_transfers; fixed scenarios for direct, one- and
  two-transfer journeys, both directions, inactive line, unreachable stop (L-52).
